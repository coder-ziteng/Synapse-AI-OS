## 0. 文档目的

定义外交工具（Diplomat）的**内部架构**：从原始构想的"网络栈最底层的海关"出发，落实为结构化业务通道（Channel）、编解码器（Codec）注册表、入出站安全扫描管道、性能分层处理。本文档回答：

1. 为什么外交工具不能是普通 socket 代理？
2. 哪些通道必须存在、各自的固定行为是什么？
3. 如何在保持"无外交即无网络"的不变量下，支持插件式扩展？
4. 性能开销怎么控制？

> ⚠️ 本文档已从骨架进入设计细化阶段；每节给出具体方案 + 待决策项（TBD）。

## 1. 设计原则

| # | 原则 | 反模式 |
|---|------|--------|
| P1 | **唯一网络出口不变量**：本机对外的所有 L2/L3/L4 字节流只能由外交工具生成；其他进程物理上无网可上 | 在多个用户态服务中分布 socket 能力 |
| P2 | **业务类型驱动协议栈**：每个外交动作必须声明业务类型，类型决定通道与编解码器；禁止"通用字节管道" | 通用 TCP/UDP 转发 + 应用层自行处理 |
| P3 | **通道强隔离**：通道间禁止跨类型转发（如文件通道的编码器不可用于视频流），防"类型混淆"攻击 | 统一编解码器 |
| P4 | **安全策略差异化**：文件 = 固化扫描；流媒体 = 实时轻量检测；API = Schema 双向校验 | 全量深度审计所有流量 |
| P5 | **编解码器可插拔**：新通道注册不修改外交工具核心 | 硬编码全部通道类型 |
| P6 | **入出站双闸**：入站文件强制扫描后落盘；出站文件强制扫描后放行；任何跳过即视为安全事件 | 仅审计不阻断 |

## 3. 不变量 #1：唯一网络出口

### 3.1 实现机制
- 内核在 Capability 创建期只为外交工具进程发放 NIC 相关的 `Device` + `IRQ_BIND` 能力（见设计文档 01 §2.1）。
- 其他进程若尝试获取 NIC 能力 → 内核拒绝并写入审计事件。
- 任何进程若尝试直接 mmap MMIO 范围（含 NIC BAR）→ 缺页处理判定为非法访问，杀进程 + 审计事件。

### 3.2 验证用例（Phase 5 退出标准）
- **E1**：在外交工具进程外，启动一个用户态测试进程，尝试注册 NIC 能力；期望：返回错误并审计。
- **E2**：在外交工具被强制 freeze 时，发起一个对外 HTTP 请求；期望：连接超时或拒绝（验证"外交冻结即断网"）。
- **E3**：尝试构造一个伪造的以太网帧绕过外交工具；期望：因无 NIC 能力，无法发出任何 L2 字节。

## 4. Channel Registry（通道注册表）

### 4.1 数据结构
```rust
// user/diplomat/src/channel.rs
pub trait Channel: Send + Sync {
    /// 通道标识符（用于路由 + 审计）
    fn kind(&self) -> ChannelKind;

    /// 处理入站业务对象（来自外部）
    fn handle_inbound(&self, ctx: InboundCtx) -> Result<(), ChannelError>;

    /// 处理出站业务对象（来自 Agent）
    fn handle_outbound(&self, ctx: OutboundCtx) -> Result<(), ChannelError>;

    /// 通道级安全策略
    fn policy(&self) -> &ChannelPolicy;
}

pub enum ChannelKind {
    File, Web, Stream, Api, Realtime, // 首期 5 类
    // 后续可扩展：Hologram, ...  (P5 可插拔)
}

pub struct ChannelRegistry {
    channels: BTreeMap<ChannelKind, Arc<dyn Channel>>,
}
```

### 4.2 注册流程
- 启动期：外交工具加载内置 5 类通道（编译期注册）。
- 运行期：通过受信 IPC 接收 `RegisterChannel` 请求 → 能力校验 + 签名校验 → 注入注册表。
  - **TBD**：是否允许运行期注册？当前建议**仅编译期注册**，避免攻击面扩大；远期可考虑受信签名 manifest。

## 5. 五类通道（首期）

### 5.1 File Channel — 文件传输
- **业务对象**：文件 + 元数据（来源、大小、类型、所有者）。
- **出站固化行为**（不可绕过）：
  1. 编码器分片 + 签名 + 元数据封装。
  2. 出站安全网关：**PII 检测**、**恶意代码静态扫描**、**敏感数据脱敏**；不通过则拒绝并审计。
  3. 经 smoltcp 发出。
- **入站固化行为**（不可绕过）：
  1. 经 smoltcp 接收 → 解码器重组。
  2. **入站安全网关强制全量扫描**（与出站同等强度）：杀毒 / 后门 / 完整性 / 数字签名。
  3. 扫描不通过 → 文件**丢弃**（不写入任何存储）+ 审计事件 + 通知发起方。
  4. 扫描通过 → 写入对应业务节点（见"安全网关→存储"边界）。
- **通道级别认证**：发件方必须持有 File Channel 的 `SEND` capability；接收方必须事先声明"接受文件"能力。

### 5.2 Web Channel — 网页浏览
- **业务对象**：URL + 请求方法 + Headers + Cookie 隔离上下文。
- **编码器**：
  - URL 规范化（防 IDN 同形异义字攻击）；
  - Header sanitization（剥离本地回环 / 内网段 IP）；
  - Cookie 隔离（每个 Agent 独立 Cookie jar）。
- **解码器**：
  - HTML/CSS/JS 解析；
  - **内容清洗**：移除危险脚本（DOM XSS sink）、广告 / 追踪器拦截；
  - **沙箱渲染**：将清洗后的内容投递给专用渲染进程（隔离环境，不与外交工具共享内存）。
- **安全策略**：**不做全量深度扫描**，靠内容清洗 + 沙箱隔离兜底。

### 5.3 Stream Channel — 音视频流
- **业务对象**：流标识 + 编解码参数（H.264/H.265/AV1/Opus）。
- **编码器**：媒体编码（必要时硬件加速）+ DRM 封装 + 码率适配。
- **解码器**：解码 + 投递给隔离媒体渲染进程。
- **安全策略**：流式数据无法做全量扫描，采用**帧级 / 包级轻量检测**：
  - 视频：检测敏感画面（如身份证、人脸）；
  - 音频：关键词监听（限本地规则集）；
  - **TBD**：检测到违规时的处置（截断？打码？熔断？）。

### 5.4 API Channel — 外部 API 调用
- **业务对象**：HTTP/gRPC 请求 + Schema 描述（请求/响应两侧）。
- **编码器**：参数校验 + Schema 校验 + 速率限制 + 身份注入。
- **解码器**：响应解析 + Schema 校验 + 数据脱敏 + 异常检测。
- **安全策略**：**双向 Schema 校验**，请求前校验参数，响应后校验结果。
- **典型用途**：Agent 调用远程 AI API（首期外交工具的"AI 原生"主路径）。

### 5.5 Realtime Channel — 实时通信
- **业务对象**：低延迟消息（语音通话帧 / IM 消息）。
- **编码器**：实时加密 + 低延迟压缩 + QoS 标记。
  - **TBD 加密协议选型**：候选 (a) DTLS 1.3 over UDP（标准、可移植）；(b) 自研 SRTP 风格轻量 AEAD（AES-GCM 128 + 4-byte 序列号，去握手开销）；(c) WireGuard 风格（Noise 框架 + Curve25519，首字节零）。首期倾向 (a) 标准路径，若性能不达标再切 (b)。
- **解码器**：解密 + 解压 + 抖动缓冲。
- **安全策略**：**极低延迟路径**——仅做关键风险点拦截（如关键词过滤、异常流量检测）；不做深度审计。

## 6. Security Gateway（安全网关）

### 6.1 入站流水线
```
[网络] → smoltcp → [Decoding] 解码器重组 → [Scan] 强制扫描 → [Persist] 落盘到业务节点
                                  ↓ 失败
                            [Audit] 写入审计事件 + 通知发起方
```

### 6.2 出站流水线
```
[Agent] → [Encode] 编码器封装 → [Scan] 出站扫描 → smoltcp → [网络]
                            ↓ 失败
                        [Audit] + 拒绝 + 通知发起方
```

### 6.3 扫描器注册表（与 Channel Registry 同构）
- 首期内置：`PII Detector`（规则 + 模型可选）、`Malware Static Scanner`（签名 + ClamAV 接口预留）、`Backend Detector`（供应链投毒）、`Watermark Embedder`（出站水印）。
- 性能开销由通道类型决定（见 §7）。

### 6.4 与存储栈的关系
- 任何持久化写入必须经过 Security Gateway（**不变量 #2**）。
- 存储栈（Phase 6 远期）需暴露"安全上下文"接口：调用方必须出示 `WRITE_TO_STORAGE` capability；网关再写入审计后调用存储。
- **TBD**：网关失败时是否熔断整个外交工具（强安全）还是仅拒绝单笔（高可用）？

## 7. 性能分层 (Performance Tiering)

原始构想明确提出的"性能 vs 安全"权衡，本节落地：

### 7.1 三级路径

| 等级 | 适用通道 | 处理内容 | 典型延迟目标 |
|------|---------|---------|--------------|
| **Fast** | Realtime / Stream（直播） | 加密 + 轻量关键词过滤 | < 10 µs / 包 |
| **Standard** | Web / API | 加密 + 身份验证 + Schema 校验 + 同步基础审计 | < 1 ms / 请求 |
| **Deep** | File（出站）/ 入站全类型 | 同上 + 深度内容扫描 + 同步全量审计 | < 100 ms / 文件 |

### 7.2 异步审计
- Fast 路径**仅做加密 + 轻量关键词过滤**（与 §7.1 表对齐），**深度审计**（异常检测、流量画像、行为围栏）由独立 worker 线程异步消费审计事件流。
- 检测到违规 → 追溯熔断（冻结相关 Agent / 切断连接）。
- Fast 路径的"轻量过滤"是**同步**的（决定能否放行），"深度审计"是**异步**的（发现违规后追溯处置）——两条路径职责严格分离。

### 7.3 硬件加速 (远期)
- 加密/签名验证下沉到网卡或专用安全芯片（IPSec offload、TLS offload）。
- **TBD**：目标硬件选型 / 是否纳入 Phase 5。

### 7.4 性能预算（对外承诺）
- 普通 Web 请求 P99 < 5 ms（含身份验证）。
- Realtime 流 P99 < 50 ms 端到端。

## 8. 审计接口

### 8.1 审计事件格式
```rust
// 由外交工具发出，与内核审计事件流合并（见 [设计文档 01 §3.5](01-capability-agent-permission-model.md) "审计钩子"）
pub struct AuditEvent {
    pub timestamp_ns: u64,
    pub actor_agent: AgentId,         // 发起方（外交工具进程或调用 Agent）
    pub channel: ChannelKind,
    pub direction: Direction,         // Inbound | Outbound
    pub peer: PeerDescriptor,         // 对端身份 + IP + 协议版本
    pub resource: ResourceRef,        // 文件 hash / URL / API 端点
    pub action: AuditAction,          // Send / Recv / Scan / Persist / Reject
    pub decision: Decision,           // Allow | Deny(reason) | Quarantine
    pub content_hash: Option<[u8;32]>,// 内容指纹（不存原文）
    pub signature: Signature,         // ★ 不透明签名（含算法标识，对齐 [Doc 06 §13.2.2](06-system-services-roadmap.md)）
                                      // 业务层事件用外交工具密钥签名；内核事件由审计服务签名
}
```

> **注**：旧版 `signature: [u8;64]` 升级为 `Signature` 类型（算法标识 + 字节序列），Phase 6 后量子密码迁移（ML-DSA / SLH-DSA）**不破坏审计事件格式**。`Signature` 类型定义见 [Doc 06 §13.2.1](06-system-services-roadmap.md)。

### 8.2 不可篡改保证

签名主体按事件来源分层（与 [设计文档 03 §6.3](03-ipc-message-and-single-copy-path.md) 一致）：

- 外交工具**只对自身产出的业务层事件**（§8.1）用外交工具密钥签名（私钥存于外交工具进程内存，永不出外交工具）。
- 内核事件（cap 校验 / IPC / 进程生命周期）由内核在事件点构造并盖 `agent_id`，经内核↔审计服务专用通道推送，外交工具无法改写（详见 [设计文档 03 §6.3](03-ipc-message-and-single-copy-path.md)）。
- 业务层事件推送到独立 Audit Service（用户态进程，独占持久化能力）后，由**审计服务自身密钥**对聚合批次签名落盘；外交工具与一般用户进程均不可改写审计存储。
- 审计服务对外暴露只读查询接口。
- **TBD**：是否需要持久化到 TPM 受保护区域？远期。

## 9. 防"类型混淆"攻击

通道隔离原则（§1-P3）的具体落实：

- 编码器在出站时携带**业务类型声明**（编译期类型保证 + 运行期校验双重保护）。
- 对端收包后**先校验类型再调用解码器**：若声明类型与通道不匹配 → 丢弃 + 审计 + 触发跨通道异常检测。
- 注册表运行期禁止通道 `kind()` 重命名。
- **测试用例**：构造一个恶意 Agent 试图把视频流伪装成文件传输；期望：跨通道异常 → 立即熔断。
