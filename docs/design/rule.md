先对此项目建立任务计划以及开发规则：
1、建立task.json，建议一个可不断更新状态以及修正任务计划的长记忆状态及任务管理文件。
2、原则：将任务分为多个小任务，每个任务都可以在一个比较小的上下文窗口中完成。
3、原则：开发前先对技术方案进行细化->论证->实现->验证。小闭环报通，并对单元测试用例进行建档，为后期组装为集成测试用例做准备。
4、开发过程中，如果遇到稳定性、效率方面的考虑，优先考虑优化稳定性->效率，绝对不能不考虑稳定性及效率，为了实现功能而糊弄。
5、系统性思维：每个功能的开发都需要在整体的框架下进行设计，禁止通过mock的方式来实现效果，而是需要每个功能都扎实设计，真实可用。
6、代码名称、目录等建立需要合理、单一职责原则，讲究抽象和可扩展。每个文件代码量不得超过1000行，核心代码的方法、参数都必须进行注释。
7、代码编写完成后必须更新任务状态（task.json)，并且更新readme.md

## README 同步维护协议（第 7 条实施细则，面向多窗口并行开发）

> 背景：项目计划在完成初版核心功能后发布到 GitHub，由更多人（与 AI Agent）共同维护。
> README.md 是新成员的第一入口，必须从第一天起保持准确、体现项目价值与架构。

8、**同步时机**：任何窗口在完成任务的代码提交时，必须在**同一提交或紧邻的下一个提交**中
   更新根目录 `README.md` 的受影响小节。禁止"以后再补"——README 落后于代码即视为任务未完成。

9、**必须检查并更新的小节**（只改受影响的，其余不动）：

   | README 小节 | 触发更新的改动 |
   | --- | --- |
   | 顶部"当前状态"引用块 | Phase 完成/推进、重大里程碑 |
   | §2 架构总览 | 新增/删除 crate、内核子系统、分层变化 |
   | §3 进度表 | 任何 task.json 任务状态变化（Phase 级汇总） |
   | §4 快速开始 | 构建/运行/测试命令、判定标准、脚本变化 |
   | §5 仓库结构 | 新增/删除/重命名顶层目录 |
   | §6 文档导航 | 新增设计文档（docs/design/NN-*.md） |

10、**并行窗口防冲突**：
    - 改 README 前先 `git status` 确认它未被其他窗口修改；若已被修改（工作区脏），
      只做**增量小编辑**（Edit 精确替换自己任务相关的行），禁止 Write 整篇覆盖。
    - 禁止还原/覆盖其他窗口的 README 改动；发现 README 内容有错先核对 task.json 再改。
    - 提交时只 `git add README.md`（连同自己任务的文件），不夹带他窗口的脏文件。

11、**写作标准**（面向 GitHub 开源 + AI Agent 读者）：
    - 价值主张与架构图放最前；新读者 60 秒内能回答"这是什么、为什么、现在到哪了"。
    - 所有命令必须实测可复制粘贴执行；判定标准写明确数值（如 QEMU 退出码 363）。
    - 状态描述与 task.json 一致，不写"大概/进行中"这类模糊词，写具体 Phase/任务号。
    - 中英文之间加空格；代码/路径用反引号；markdown lint（MD040/MD060 等）零警告。

12、**设计文档索引联动**：新增设计文档时同步更新 `docs/README.md` 的状态总览表
    （该文件归属设计窗口时，遵守第 10 条同样的防冲突规则）。
