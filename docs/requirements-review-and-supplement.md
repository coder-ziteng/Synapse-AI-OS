# Synapse 需求评审与补充方案

> 状态：PROPOSED  
> 评审对象：[需求目标.md](../需求目标.md) 及 `docs/design/` 下 01-03 设计文档  
> 评审日期：2026-09-25  
> 目的：识别当前目标与路线图中尚未明确、但会影响实现正确性、可验证性和后续扩展的事项，并给出可执行的补充方案。

---

## 1. 评审结论

当前方案已经明确了核心方向：Rust、单核 x86_64、微内核、用户态驱动、Capability、同步 IPC、QEMU 验证，以及首期将“AI 原生”收敛为远程 API 代理。整体方向可行。

但目前仍有一个结构性问题：很多目标描述了“要支持什么”，却没有定义“何时算完成、失败后如何恢复、边界条件是什么”。如果直接进入 Phase 2-4，最可能出现的不是单点代码问题，而是模块之间的语义不一致：

1. IPC、Capability、进程生命周期和资源回收缺少统一的对象生命周期模型。
2. NFR1/NFR2/NFR3 是目标值，但没有测试环境、统计方法和允许的例外。
3. 用户态 ABI、ELF、syscall、initramfs 仍有多个 TBD，无法稳定地产出用户态程序。
4. 用户态驱动、DMA、IRQ 和网络代理的安全边界尚未形成完整威胁模型。
5. 路线图缺少可取消的范围闸门，个人开发者容易在 Phase 4 发生范围膨胀。

建议：不改变现有总体架构，增加一层“项目级契约”，并在进入 Phase 4 前完成本文第 6 节列出的设计决策。

---

## 2. 已识别的需求缺口

### 2.1 缺少明确的 MVP 和退出标准

现有 Phase 列表以任务清单为主，但“能跑起来”尚未被定义为可自动判断的验收条件。尤其是：

- FR2 没有区分物理页分配、内核映射、用户映射和回收是否都必须完成。
- FR3 没有定义调度公平性、优先级语义和线程退出后的资源回收。
- FR4 没有明确消息截断、非法用户指针、超时、取消和发送方死亡的行为。
- FR5 没有定义 ELF 装载失败的错误分类，也没有明确第一个用户进程的最小能力集。
- FR6/FR7 没有定义能力撤销和 IRQ 解绑在并发/在途操作中的一致性。

**补充方案：** 每个 Phase 必须有“可执行退出测试”，而不是仅有勾选项。退出测试应包含输入、环境、期望串口输出、退出码或 QEMU 状态。

### 2.2 NFR 的测量口径不完整

- “IPC 微秒级”没有定义消息大小、CPU 型号、QEMU 参数、优化级别、是否包含调度和日志。
- “内核 ELF 小于 2MB”没有定义 debug/release、strip、链接时垃圾回收和是否包含符号。
- “Safe Rust 100%”与启动代码、页表、上下文切换、用户指针访问、端口 I/O 的必要 `unsafe` 存在冲突。
- “新增架构无需修改核心代码”没有定义哪些 Trait、类型和测试是稳定接口。

**补充方案：** 采用基准配置和指标分层：

| 指标 | 首期验收口径 |
|---|---|
| 内核体积 | `release`、去除调试符号后的 bootable kernel ELF，记录体积；debug 仅作开发产物 |
| IPC 延迟 | QEMU 固定版本、固定 vCPU/内存、关闭串口日志，分别测寄存器消息和 4 KiB 消息的 p50/p95/p99 |
| 上下文切换 | 两个可运行线程之间连续切换，报告 p50/p95/p99，不把首次冷启动混入结果 |
| Safe Rust | 核心层禁止新增未封装 `unsafe`；架构层和边界封装层允许，并对每处写明不变量 |
| 可移植性 | fake HAL 的宿主测试必须通过；核心 crate 不得直接依赖 x86 特有类型 |

### 2.3 对象生命周期和资源上限没有统一定义

Capability、Endpoint、Notification、Process、Thread、MemoryRegion 和 IRQ 绑定之间存在引用关系。当前文档分别描述了它们，但没有规定：

- 对象何时进入销毁态，何时真正释放。
- 持有 capability 是否等价于持有对象引用。
- 进程退出后，其他进程持有的 capability 如何处理。
- Endpoint 上的发送者/接收者死亡时，阻塞线程如何唤醒。
- cap table、线程数、地址空间区间、消息长度和共享内存 grant 是否有上限。

**补充方案：** 引入统一对象状态机：

```text
Live -> Revoking -> Retired -> Freed
```

Capability 指向带 generation/version 的对象句柄，而不是可复用的裸 slot。slot 重用时 generation 必须变化，避免 use-after-free 和旧句柄复活。所有内核对象都必须声明：

1. 最大数量或配额来源；
2. 引用关系；
3. 退出/撤销时的唤醒规则；
4. 最终释放责任方；
5. 失败时是否回滚。

### 2.4 资源配额和拒绝服务防护缺失

能力模型解决“能不能做”，但没有解决“能做多少”。恶意或失控 Agent 可以耗尽：

- 页帧和内核堆；
- cap table 槽位；
- Endpoint 队列；
- 线程和地址空间区间；
- IRQ 通知；
- 共享内存 grant；
- 网络请求和 TLS 资源。

**补充方案：** Phase 4 引入最小配额模型：每个进程拥有 `Quota`，至少限制页帧、线程、cap、Endpoint、消息大小和未完成 IPC 数量。超限统一返回明确错误码，不允许隐式阻塞或内核 panic。配额本身由父进程 capability 控制，root/init 拥有初始预算。

### 2.5 ABI 和版本演进未纳入范围

当前 syscall 号表、消息头和 Capability 权限位都是草案。如果没有版本策略，用户态程序一旦编译就会和内核强绑定。

**补充方案：**

- syscall ABI 增加版本查询（例如 `abi_query`），只承诺已发布版本。
- 消息头增加 `version`、`header_len` 和 flags 的保留语义。
- 所有结构体明确字节序、对齐、大小和兼容策略，禁止直接把 Rust 私有布局当 ABI。
- 错误码采用固定的正数枚举，syscall 返回 `Result` 的稳定编码，不复用宿主 OS 的未承诺扩展。
- Capability rights 只允许追加；删除或重解释权限位必须提升 ABI major 版本。

### 2.6 安全威胁模型仍不完整

目前记录了无 IOMMU、无 KPTI 和 `agent_id` 伪造风险，但还缺少攻击者能力和安全目标的完整边界：

- 用户态进程是否可能恶意或仅假定“外交工具可信”？
- root/init 被攻破后，内核是否仍需保护其他进程？
- 用户指针、长度、整数溢出和地址区间重叠如何验证？
- Capability token 是否需要保密、不可转移，还是仅需不可伪造？
- 网络代理如何处理 TLS 密钥、证书、重放、超时和外部 API 凭证？
- 串口日志是否可能泄露 token、请求体或外部凭证？

**补充方案：** 在首期明确两种安全等级：

1. **内核边界安全（必须）**：恶意用户进程不能越权访问内核、其他地址空间或未授权设备；所有用户输入经过长度、对齐、溢出和权限检查。
2. **设备 DMA 安全（明确不保证）**：无 IOMMU 时，Phase 1-5 将拥有 DMA 能力的用户态驱动视为 trusted computing base，并在启动日志和文档中显式声明。

同时增加安全测试：非法 cptr、过期 generation、权限降级绕过、跨页用户缓冲区、长度溢出、重复回收、进程退出时在途 IPC，以及伪造 `agent_id`。

### 2.7 故障、恢复和可观测性不够具体

已有 panic 日志和串口输出，但还没有定义用户进程 fault、内核 bug、设备异常和网络失败的统一诊断格式。

**补充方案：**

- 内核 panic：输出版本、commit、CPU 状态、异常向量、错误码、RIP/RSP、当前线程和 fault 地址，然后停止或按测试模式退出。
- 用户进程 fault：记录 `agent_id`、进程 ID、fault reason、地址、RIP、syscall 号；仅杀死故障进程，不得直接 panic 内核。
- IPC 错误：区分 `InvalidArgument`、`PermissionDenied`、`WouldBlock`、`Timeout`、`PeerDied`、`BufferTooSmall` 和 `ResourceExhausted`。
- 设备异常：驱动超时、IRQ 风暴和 PCI 配置错误必须可诊断，并有隔离/解绑路径。
- 日志等级和脱敏规则在 Phase 1 固定；release 默认不输出敏感 payload。

### 2.8 启动、构建和供应链缺少可复现性要求

工具链已计划锁定 nightly，但还需要锁定构建输入和验证方式：

- Cargo.lock 是否提交并在 CI 中使用 `--locked`；
- bootloader、QEMU 和 Rust nightly 的兼容矩阵；
- 外部 crate 的许可证、维护状态和 `unsafe` 风险；
- 镜像是否包含可追踪的版本信息；
- 无网络环境是否能复现构建。

**补充方案：** Phase 1 增加 `xtask verify`，统一执行格式检查、宿主测试、交叉编译、镜像生成和 QEMU smoke test。CI 使用固定工具链、`cargo --locked`，并上传镜像、串口日志和测试摘要作为构建产物。

### 2.9 网络代理的产品边界尚未落地

“远程 API 代理”已作为首期 AI 目标，但还缺少最小协议和安全边界：

- 支持哪些协议（HTTP/1.1、HTTPS、DNS、TCP）；
- 请求/响应最大尺寸和超时；
- 凭证存放与传递方式；
- API 错误如何映射为 IPC 错误；
- 网络不可用时 Agent 是否重试，是否有退避和幂等要求；
- 是否允许任意目标地址，还是仅允许白名单。

**补充方案：** Phase 5 先实现受限 API：固定 HTTPS 出站、域名白名单、连接/读取/总请求超时、最大请求体/响应体、有限次数指数退避，并禁止把凭证写入普通日志。把“任意网络栈”列为非目标，避免外交工具演变成未定义的通用操作系统服务。

### 2.10 系统服务路线与内核路线缺少依赖治理

`docs/design/06-system-services-roadmap.md` 规划了 S1-S6 服务层，但目前存在几个容易冲突的依赖：

- S1 的配置中心提到 SQLite，而存储栈被放在内核 Phase 6；没有临时存储方案就无法验收 S1。
- S3 需要内核提供 CPU 时间核算、配额 enforcement 和 freeze 原语，但这些能力没有在 P1-P6 中明确排期。
- S4 依赖持久化、向量数据库和图数据库，工作量明显大于“内核可用后即可并行”的默认假设。
- S5 的 WASM 沙箱和多 Agent 安全边界没有对应的隔离、系统调用和资源预算契约。

**补充方案：** 为系统服务增加“依赖级别”：

1. `P0`：不依赖持久化的内存态服务，可在 QEMU 上演示；
2. `P1`：依赖内核 IPC、进程和配额，但可使用 host-side/mock storage；
3. `P2`：依赖真实存储、网络或 GPU，必须等相应内核能力完成。

S1/S2 首期只承诺 `P0/P1`。配置中心先使用 initramfs 中的只读配置和内存态 KV；SQLite、向量库、图数据库和自进化回滚统一移到 P2。每个 S 阶段也必须有独立退出测试，不能以“内核 Phase 完成”自动视为服务层完成。

### 2.11 外交工具设计超出首期产品范围

设计文档 04 同时定义 File、Web、Stream、API、Realtime 五类通道、深度扫描、媒体检测、内容清洗、审计持久化和插件注册。这与需求目标中“Phase 5 首期仅做远程 AI API 代理”不一致，可能把一个可验证的端到端目标膨胀成通用网络平台。

**补充方案：**

- Phase 5 只实现 API Channel 的最小子集：HTTPS、固定域名白名单、请求/响应 schema、超时、限流、审计摘要。
- File/Web/Stream/Realtime 仅保留接口草案和威胁模型，不进入 Phase 5 退出标准。
- Channel Registry 首期采用编译期静态注册，不支持运行期插件注入。
- 安全网关首期只做策略拒绝、大小限制、凭证脱敏和审计摘要；恶意代码扫描、媒体内容理解、全量 PII 扫描需单独立项。

### 2.12 远期跨 OS 协议需要兼容性约束，但不应提前实现

文档 05 将 DID、VC、SD-JWT、信誉、行为契约和多个外部 Agent 协议列为远期方向。当前需要避免的是 Phase 5 写出无法演进的内部格式，而不是提前实现完整的跨 OS 信任体系。

**补充方案：** Phase 5 只为外交请求保留 `protocol_version`、`request_id`、`channel`、`expires_at`、`payload_hash` 和扩展字段；内部 `agent_id` 不直接暴露到网络。DID/VC/信誉/自动仲裁不作为 Phase 5 依赖。引入任何外部协议前，另行记录版本、规范来源、许可证和互操作测试，不以文档中的候选列表自动视为已选标准。

## 3. 需要修正或澄清的现有表述

### 3.1 “单拷贝”命名

跨地址空间把发送缓冲区复制到接收缓冲区，仍然发生一次数据复制；它不是数据零拷贝。建议统一表述为：

- 小消息：寄存器/内核保存区 fast path；
- 普通消息：跨地址空间一次复制（single-copy）；
- 大对象：预授权共享页描述符（zero-copy data path）。

这样可以避免性能目标和实现预期不一致。

### 3.2 “Safe Rust 100%”

建议改为“核心逻辑的内存安全由 Safe Rust 和封装不变量保证”。启动、页表、上下文切换、端口 I/O、用户指针和 DMA 映射不可避免地需要 `unsafe`；真正可验收的是 `unsafe` 的范围、审查记录和测试覆盖，而不是字面上的 100%。

### 3.3 PCID 不应成为 Phase 4 的硬前置

PCID 依赖 CR4/INVPCID、地址空间切换策略和 CPU 能力检测。建议先实现正确的无 PCID 路径，再以可选优化加入 PCID，并分别测量性能。不能因为 PCID 延迟而阻塞第一个用户态进程。

### 3.4 “用户态可多线程”应后置

首个用户态进程建议先限制为单线程。待地址空间、syscall、fault、退出回收稳定后，再开放同进程多线程。否则进程、线程、地址空间和 death notification 会同时引入过多交叉状态。

### 3.5 服务层不应反向扩大内核职责

记忆、自进化、Agent 编排、通道策略、审计查询和动态 UI 都应留在用户态服务。内核只提供隔离、调度、内存、IPC、能力和最小计量原语。任何新增内核 syscall 都必须说明为何不能由现有 IPC + 用户态服务组合实现，并补充安全边界和测试。

## 4. 补充后的最小可行范围（MVP）

### MVP-1：可引导、可测试的内核

- x86_64 BIOS + QEMU + 固定 nightly；
- 串口日志、panic 诊断、QEMU test framework；
- fake HAL 宿主测试和 CI；
- 一个可重复生成的 bootable image。

### MVP-2：单核内核任务

- 物理页分配、内核堆、IDT/TSS、page fault；
- 内核线程、阻塞/唤醒、退出回收；
- Round-Robin，优先级只保留最小语义；
- 明确锁、中断屏蔽和调度点不变量。

### MVP-3：单线程用户态

- 固定静态 ELF 格式和 initramfs 格式；
- 单进程、单线程、固定初始地址空间布局；
- 最小 syscall：`yield`、`exit`、`gettime`、`ipc_send/recv/reply`；
- 用户指针校验和用户 fault 隔离；
- 不要求 PIE、动态链接、按需分页和 PCID 同时首发。

### MVP-4：可信服务 IPC

- 单接收者 Endpoint、同步 RPC、寄存器 fast path；
- 普通消息最大长度固定；
- 共享内存 grant 仅支持显式预映射页；
- Capability 创建、委托、撤销和 generation 检查；
- cap transfer 失败时事务性回滚。

### MVP-5：受限网络演示

- 用户态 virtio-net 驱动；
- 单个外交工具服务；
- 固定 HTTPS API 白名单；
- Agent → IPC → 外交工具 → 网络设备 → API 的端到端测试；
- 设备驱动被视为 trusted computing base，并记录无 IOMMU 限制。

## 5. 推荐的跨模块契约

| 契约 | 规则 | 责任模块 |
|---|---|---|
| 地址 | 所有用户地址、长度、区间运算先做溢出检查 | syscall/mm |
| 对象引用 | 使用 `object_id + generation`，禁止把 slot 地址当永久句柄 | cap/object |
| 阻塞 | 阻塞操作必须有可定义的唤醒原因：完成、取消、超时、对端死亡 | sched/ipc |
| 错误 | 内核错误不得通过 panic 表达；必须映射为稳定错误码 | syscall/all |
| 回收 | 进程退出先撤销能力和唤醒等待者，再回收页和内核对象 | process/cap/ipc/mm |
| ABI | 所有跨边界结构固定布局、大小、版本和对齐 | user/ syscall/ipc |
| 日志 | release 不记录 payload、凭证和 capability 原始值 | kernel/user |
| 测试 | 每个安全边界至少有正常、边界、非法和资源耗尽用例 | CI/all |

## 6. Phase 4 前必须收敛的决策

以下决策建议作为 Phase 4 的硬性闸门；没有结论时不得开始大规模实现：

1. 用户态 target、链接脚本、静态 ELF 类型和固定地址布局。
2. initramfs 格式、打包工具和 `/init` 启动约定。
3. syscall ABI 版本、错误码、用户指针验证和阻塞/超时语义。
4. Endpoint、Notification 的对象状态、等待队列和对端死亡规则。
5. Capability 的 generation、委托链、撤销范围和 cap transfer 回滚。
6. 进程/线程退出顺序、death notification 和资源回收顺序。
7. 每进程资源配额与 root/init 的预算授予方式。
8. 普通消息最大长度、共享内存 grant 的生命周期和权限。
9. 缺页策略：首期预映射还是按需分页；若按需分页，明确缺页期间的锁规则。
10. IPC 和上下文切换基准的固定硬件/QEMU 配置及统计脚本。
11. S1-S6 服务层各阶段的依赖级别、mock 策略和独立退出标准。
12. Phase 5 外交工具只实现 API Channel，其他通道和跨 OS 身份协议的延期边界。

## 7. 更新后的里程碑退出标准

### Phase 1

`xtask verify` 在干净环境下成功完成格式检查、宿主测试、release 构建、镜像生成和 QEMU smoke test；串口输出包含版本和 `Hello, Synapse!`。

### Phase 2

测试覆盖正常页分配、耗尽、双重释放、非法页表权限、page fault、double fault 兜底；内核 panic 能输出最小诊断信息。

### Phase 3

至少两个内核线程完成运行、阻塞、唤醒和退出；调度器在定时器抢占和显式阻塞两条路径上都能通过测试；无在中断上下文切换的实现。

### Phase 4

第一个用户态程序可启动、调用 `gettime/yield/exit`、执行一次合法 IPC，并在非法 syscall、非法指针和权限不足时仅自身失败。Capability 撤销后旧句柄必须稳定返回错误。

### Phase 4.5

QEMU virtio PCI 设备可枚举；合法 IRQ 可通知用户态；未 ack 的 IRQ 触发限流/屏蔽；解绑后不再投递通知。

### Phase 5

端到端 HTTPS 代理演示可重复执行；网络超时、DNS/连接失败、API 非 2xx、超大响应和外交工具退出都有明确错误和恢复行为。

## 8. 建议新增的测试矩阵

| 层级 | 必测内容 |
|---|---|
| 宿主单元测试 | Cap rights、generation、撤销、配额、Endpoint 队列、消息编解码、错误码 |
| 属性/模糊测试 | ELF 段边界、消息头长度、cap transfer、用户地址区间、initramfs 目录解析 |
| QEMU 集成测试 | 页表权限、Ring 3 切换、syscall、page fault、进程退出、IRQ 通知 |
| 性能测试 | fast path round-trip、4 KiB single-copy、上下文切换、日志关闭与开启对比 |
| 故障注入 | 内存耗尽、cap table 满、对端退出、设备不 ack、网络超时、损坏 ELF |
| 安全回归 | 伪造 agent_id、越权 capability、旧句柄复用、跨进程地址访问、整数溢出 |

测试报告至少保存：工具链版本、QEMU 版本、CPU/内存参数、commit、随机种子、串口日志和失败用例。

## 9. 风险登记补充

| 编号 | 风险 | 影响 | 建议处置 |
|---|---|---|---|
| R9 | ABI/对象生命周期未收敛导致 Phase 4 返工 | 高 | Phase 4 闸门前完成第 6 节决策 |
| R10 | 无配额导致单个 Agent 耗尽内核资源 | 高 | MVP-4 引入 per-process quota |
| R11 | “单拷贝”被误解为零拷贝，性能目标失真 | 中 | 统一术语并分别测量三条路径 |
| R12 | 用户态 fault/对端死亡导致内核等待队列泄漏 | 高 | 先定义退出和唤醒顺序，再实现 IPC |
| R13 | nightly/crate/QEMU 组合不可复现 | 中 | `Cargo.lock`、固定工具链、`xtask verify`、CI 产物 |
| R14 | 远程 API 代理范围膨胀为通用网络栈 | 中 | 白名单、限流、超时和明确非目标 |
| R15 | 无 IOMMU 下 DMA 破坏内存 | 高 | 显式信任边界；Phase 6 引入 IOMMU |

## 10. 执行顺序建议

1. 先把本文第 6 节的决策转化为 `docs/design/01-03` 中的最终约定，删除已决策项的 TBD。
2. 在仓库根目录补充 `xtask verify`、CI 和测试矩阵；先让“验证链”跑通，再继续增加内核功能。
3. 先实现单线程用户态和最小 syscall，不要同时引入 PIE、按需分页、PCID、多线程和动态链接。
4. 在 IPC 稳定后加入 Capability 委托/撤销和进程死亡测试，再接入 IRQ。
5. 最后实现受限网络代理，用端到端演示验证路线图，而不是以“网络栈代码完成”作为成功标准。

本文不是新增功能清单，而是对现有目标增加可验证的边界和决策闸门。若后续资源有限，应优先保留：内核边界安全、对象回收正确性、可重复测试链和 Phase 5 端到端演示；PCID、PIE、按需分页、多线程、本地推理和 IOMMU 可继续后移。
